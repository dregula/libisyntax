# iSyntax v1 to DICOM WSI: colour conversion (YCoCg-R to YBR_RCT or RGB)

Date: 2026-11-26 (split out of [iSyntax_to_DICOM_WSI_Transcoding_Claude.md](iSyntax_to_DICOM_WSI_Transcoding_Claude.md), "the Transcoding doc", which holds geometry, halo algorithm, tiling, spec reading, EBCOT sizes and tile omission). Content is unchanged except for renumbering: former section 6 = **C1**, 8d = **C2**, 8i = **C3**.
Tags: **[verified]** = measured in this repo on the real file or by numerical test; **[spec]** = from the standards; **[hypothesis]**; **open** = not decided or not measured.

Question answered here: iSyntax stores Y, Co, Cg (YCoCg-R, lifting with a halving). DICOM wants YBR_RCT (C1, C2) or RGB (C3). How is the conversion done, how exact is it, and what does it cost in size?

Short answer: **exact conversion is done in the pixel domain and destroys the sparsity that quantizer and deadzone created (YBR_RCT 2.1x, RGB 3.0x the iSyntax bytes); conversion in the wavelet domain stays sparse (YBR_RCT 0.9-1.0x) but is biased (YBR_RCT chroma up to -5, RGB all channels up to 8 levels).** The halving convention is **truncation (`fix`, C/MATLAB `/2`)**: inferred from the Philips SDK's own RGB output (C1, measured 2026-11-26), assuming the scanner's forward is the pair of the SDK's inverse. Consequence: for YBR_RCT, Cb and Cr come out exact but Y' = Y is wrong by -1 in about 64 % of tissue pixels. Fidelity target: **open, owner's decision.**

Colour-related material that stays in the Transcoding doc: YBR_RCT equations and photometric rules (8b, 8c: SGcod = 1 requires YBR_RCT), per-scale sparsity of Y/Co/Cg/Cb/Cr and the colour-transform bit cost (8e), real OpenJPEG sizes per route (8g), the fill colour for omitted glass tiles (8h). Tools: `colour_ebcot_probe.py`, `colour_bias_by_levels.py`, `colour_sparsity_cost.py`, `colour_dc_fix.py`, `rct_ycocg_vs_rct.py`, `ll_probe.py`, `rgb_route_probe.py` (all in `tools/v1_analysis/`, see its README.txt).

## C1. Colour space (YCoCg-R to YBR_RCT) **[measured, see C2]**

- Algebra: Y' = Y, Cb = -Co/2 - Cg, Cr = Co/2 - Cg (determinant 1). **[verified numerically]** (`rct_ycocg_vs_rct.py`, subsampled RGB cube).
- If the encoder's forward used floor (`>>1`): the direct conversion with `>>1` is bit-exact (Y', Cb, Cr). If it used `fix` (truncation, the Philips compression samples): Cb and Cr are exact with truncating halves, but Y' = Y is wrong by -1 in 37.5 % of colours of the RGB cube (63-65 % of the pixels of real tissue frames). Mismatched conventions give Cb/Cr off by 1 in 25 %.
- **Convention resolved by the Philips SDK output (measured 2026-11-26, `PAS.isyntax`, `compare_sdk_tiff_tiles.py`).** The SDK's LZW TIFF levels 2, 3 and 5 (RGB) were compared with libisyntax tiles of both builds (runs `20261126_130613_meson-default_PAS` = scalar truncating `/2`, and `20261126_130638_cmake-native_PAS` = SIMD floor `>>1`, in `../c_decoder_output/`; tile offsets found by search, level 5 (-23,-23), level 3 (+1,+1) relative to a 765/2^L padding estimate): **the truncating build matches the SDK in 100.00 % of the pixels on all 22 tiles tested (levels 2, 3, 5; chroma-active pixels 79-99 %), the floor build in only 25-37 %** (R and B differ in about 45 000 of 65 536 pixels, max |d| 2). So the SDK's YCoCg -> RGB inverse halves with truncation. Under the assumption that the scanner's forward is the pair of that inverse (a lossless design needs the pair; also the Philips compression sample's forward is `fix`, CLAUDE.md), **the forward convention is truncation, and the Philips viewing sample's floor is not what the product uses.** The forward itself is not observable in any file: the stored data are already quantized and the lifting is a bijection either way. **Limits:** (1) this proves the SDK decoder's inverse, not the scanner's forward; (2) one file (PAS, same Q2 parameter set as the others); (3) I cannot rule out that the "SDK" TIFF writer shares code with libisyntax: see the next point.
- **The SDK does not clamp below 0 either.** In two tiles (level 5 (8,5) and (9,6)) three pixels have an inverse value below 0: libisyntax's scalar path wraps them to 254 / 239 (R -17 -> 239), the SIMD path saturates to 0, and **the SDK TIFF holds the wrapped values** (e.g. SDK (239, 70, 136) = scalar; SIMD (0, 70, 137)). So the SDK has the same unclamped uint8 cast as the scalar C code. This is the same behaviour down to the bug, which fits Philips' reference decoder being the source of the scalar path (hypothesis) and makes an independent implementation unlikely to match on such pixels. For DICOM, such pixels must be clamped (or the wrap reproduced); about 3 per 16 level-5 tiles here.
- **What it means for the routes.** YBR_RCT: with truncating forward, Cb = -trunc(Co/2) - Cg and Cr = Cb + Co are exact; Y' = (R + 2G + B) >> 2 differs from Y by -1 in 63-65 % of tissue pixels (section above), so Y must be recomputed in the pixel domain (the 'hybrid' of C2, or Y dense) or accepted as off by 1. RGB: the exact route is the truncating inverse, 'E-fix' in C3 (sizes 3.1x tissue, 2.9x edge, 3.4-3.5x glass at 256-1024 px; slightly smaller than E-floor on glass). The earlier wavelet-domain results (C2, C3) used floor and truncation alike and showed the same bias, so they stand.
- **Left open:** a second SDK file (an independent scan would test point 2), an SDK export at level 0 or 1 (the level-1 TIFFs are truncated; the level-0 'software' TIFF is YCbCr 2x2-subsampled and lossy), and the SDK's own source or documentation for the forward.
- **RGB as the target instead of YBR_RCT:** measured in section C3 (every channel carries Y; exact route 3.0x vs 2.1x the iSyntax size; wavelet-domain route biased in all channels).
- **Correction of an earlier expectation:** a per-coefficient (wavelet-domain) conversion is **not** "off by about 1". It has a systematic bias that grows with the number of decomposition levels (section C2).

## C2. Colour conversion strategies, measured **[verified on `1.isyntax`; scripts `colour_ebcot_probe.py`, `colour_bias_by_levels.py`, `colour_sparsity_cost.py`, `colour_dc_fix.py`]**

Data needed: Cb and Cr at a position need Co and Cg at that position (Y is not needed for chroma if the forward used floor). All three colours of a region sit in the same chunk (colour-major), so mustering the three channels costs no extra chunk reads, only the 3x memory already counted in section 5 of the Transcoding doc.

**Wavelet-domain conversion** (`Cb = -q(Co) - Cg`, `Cr = Cb + Co`, `Y' = Y`, applied to LL and every detail band of the frame's own pyramid, then decoded):
- Rounding in `q()` is not the problem: at the two finest levels Co is even almost everywhere (0.3 % and 1.1 % odd; the quantizer leaves multiples of 16 and 4), at coarser levels about 50 % are odd.
- The problem is that the floors inside the reversible lifting do not commute with the colour combination: the decoded Cb differs from the pixel-domain Cb by a **bias that grows by about -0.6 per level for Cb and -0.4 for Cr**: mean error D=1: -0.62, D=2: -1.30, D=3: -2.55, D=4: -3.73, D=5: -4.88 (Cb, tissue, 256 px; Cr: -0.37 ... -3.01). A random-image control shows the same effect, so it is not a bug. At D = 5, Cb is exact in 0.1 % of pixels (max error 10), RGB differs in about 100 % of pixels (max 6-7). `q=floor` and `q=trunc` behave alike. The bias depends on content (frame of mostly flat padding: -1.0; tissue: -5.0; glass: -4.3).
- A constant correction added to the LL band shifts the whole decoded plane exactly, so the mean bias can be removed, but only per tile (a global constant fits tissue but over-corrects the flat scan-edge frame by +3). After a global fix on 512-px frames: Cb error std 1.3, range about -7..+6, Cr std 1.2; 97-99 % of pixels have RGB within 2 levels on tissue and glass, 25 % on the scan-edge frame. Near-lossless at best.

**Pixel-domain conversion** (decode Co and Cg pixels, form Cb and Cr exactly, run the frame's forward transform): exact relative to the chosen convention, and no halo problem for chroma at all, but it **destroys the sparsity** that iSyntax's quantizer and deadzone created. Cb detail coefficients, tissue frame 1024 px (non-zero fraction, zero-order entropy per coefficient): level 1: 0.12 % and 0.02 b (wavelet domain) versus **62.7 % and 1.44 b** (exact); level 2: 4.4 % and 0.42 b versus 65.5 % and 2.12 b; levels 3 to 5 about the same either way. Cr is similar (43 % and 1.27 b at level 1). Level 1 holds three quarters of all coefficients, so this is a large size increase in tissue; I did not extrapolate to the whole file (blank glass stays zero). If the forward convention was `fix`, Y' = Y + delta (delta in {-1, 0}, 63-65 % of tissue pixels) and Y would lose its sparsity in the same way.

**Hybrid:** copy-and-patch Y (exact only if the forward used floor), recompute chroma in the pixel domain. Same chroma cost as above.

Trade-off, not a free lunch: wavelet-domain = sparse and small but chroma off by a drifting few levels; pixel-domain = exact (against one chosen convention) but chroma fine bands become dense. **Decision needed from the project owner: the fidelity target for the DICOM file relative to the iSyntax decode.** **open**

## C3. Target RGB instead of YBR_RCT **[verified on `1.isyntax`; script `rgb_route_probe.py`; raw output in `$SOURCEROOT/transcoding_review/rgb/`]**

Setting: Photometric Interpretation RGB, JPEG 2000 codestream with SGcod = 0 (no component transform; PS3.5 allows it, section 8c of the Transcoding doc, and notes it compresses poorly). R, G, B are three independent components, each with its own 5/3 pyramid. Same frames, same OpenJPEG settings as 8g of the Transcoding doc (independent frames, D = 5, 64 x 64 code-blocks, `mct=0`).

- **Algebra.** YCoCg-R inverse: t = Y - h(Cg), G = t + Cg = Y + ceil(Cg/2), B = t - h(Co), R = B + Co. Linear part: G = Y + Cg/2, B = Y - Cg/2 - Co/2, R = Y - Cg/2 + Co/2. Unlike YBR_RCT, **every** output channel contains Y. There is no "Y' = Y passes through untouched" case (section C1).
- **The pixel-domain result is the libisyntax output.** The exact route is just the decoder's `ycocg_to_rgb` plus the clamp to 0..255 (clamped pixels are counted in the table; up to 2951 of 1M in the tissue-edge 1024 frame). So the RGB target needs **no** knowledge of the scanner's forward convention beyond what the decoder already fixes, but it inherits the build dependence: the floor (`>>1`) and truncating (`/2`) inverses differ in about 64 % of pixels (CLAUDE.md), so the DICOM pixels equal one specific build's output. For YBR_RCT the convention question was open until C1's SDK test; for RGB it is replaced by "which build is the reference", and the SDK matches the truncating (scalar) build, so that is the build to use. **Decision (use the truncating inverse and clamp): proposed, not yet taken.**
- **Wavelet-domain conversion is biased in all three channels** (Part A; coefficient-wise inverse on LL and all detail bands of the frame's own pyramid, versus the exact pixel-domain RGB with the same halving). Mean error by D = 1..5, tissue 256: G +0.12, +0.26, +0.52, +0.75, +1.00; B -0.25, -0.51, -0.99, -1.42, -1.84; R about 0 (+0.00 to +0.05). Std 1.1-1.3 at D = 5. At D = 5 the share of pixels exact per channel is only R 31 %, G 24 %, B 11 %, and 99.7 % of pixels differ in at least one channel (max |d| 7; 6-8 on tissue edge and glass). Floor and truncating halving behave alike. Compare YBR_RCT (C2): Y exact, Cb -4.9, Cr -3.0 at D = 5. The RGB bias is smaller per channel but touches every channel, so RGB is no better than YBR_RCT for a wavelet-domain route, only differently wrong. The explanation is the same: h() inside the lifting does not commute with the colour combination. Per-tile DC corrections of the LL band (C2) would apply here too (not measured).
- **Sparsity** (Part B, tissue 1024, level 1 = finest, non-zero detail coefficients): stored Y 5.75 %, Co 0.12 %, Cg 0.11 %. Wavelet-domain R/G/B stay at 5.8 % (0.41 bit per coefficient), i.e. exactly Y's sparsity, because Co and Cg are almost all zero there. The exact pixel-domain conversion makes them dense: G 33 % (1.59 b), R 42 % (1.80 b), B 48 % (1.81 b). Level 2: 85.7 % either way; coarser levels dense either way. Tissue edge: 3.6 % versus 25 / 34 / 41 %. This is the same mechanism as for Cb/Cr in C2 (the floor of a smooth plane is a staircase), now hitting the finest level of all three channels instead of only the chroma. Level 1 holds three quarters of the coefficients.
- **Sizes** (Part C, 2048 x 2048 regions, multiples of the iSyntax bytes of the same area; "RCT" rows reproduce 8g of the Transcoding doc in the same run):

| region, frame | RGB exact (floor) | RGB exact (fix) | RGB wavelet-dom. (biased) | YBR_RCT exact | YBR_RCT wavelet-dom. |
|---|---|---|---|---|---|
| tissue, 256 | 3.15x | 3.16x | 1.84x | 2.14x | 0.99x |
| tissue, 1024 | 3.12x | 3.12x | 1.78x | 2.09x | 0.93x |
| tissue edge, 256 | 2.95x | 2.97x | 1.68x | 2.14x | 0.97x |
| tissue edge, 1024 | 2.92x | 2.93x | 1.62x | 2.10x | 0.91x |
| blank glass, 256 | 3.76x | 3.46x | 1.77x | 3.19x | 0.97x |
| blank glass, 1024 | 3.69x | 3.39x | 1.67x | 3.12x | 0.88x |

  Absolute: tissue 256 px, exact RGB 7.18 bits/px versus 4.86 (RCT) and 2.28 (iSyntax). All streams round-trip losslessly through OpenJPEG. In the RGB columns the clipped-pixel counts are the same as for the exact RCT column (clip counts for the RCT rows are not printed by the script; the arrays are shared).
- **Why even the sparse RGB route is 1.6-1.8x.** iSyntax stores luminance once, with quantizer and deadzone shaping it. With RGB, the same Y detail is repeated in three components and nothing decorrelates them, so a floor of about 3x Y's bytes is expected. Y is the bulk of the stored bits (8e of the Transcoding doc), which matches 1.8x. YBR_RCT stores it once. Conclusion: **RGB costs about 1.5x (exact route: 3.0x versus 2.1x) the size of YBR_RCT for the same fidelity, and has no route that is both small and exact.** The only sparse RGB route is the biased one, at 1.7-1.8x the iSyntax bytes with errors up to 8 levels, which is worse in fidelity and size than the biased YBR_RCT route (0.9-1.0x).
- **Consequences.** The omitted-tile estimates of 8h of the Transcoding doc would scale up by roughly the same factor for the RGB pyramid (not measured; 8h used the RCT routes). Frame-edge halo handling (sections 2-4 of the Transcoding doc) is unchanged: it works on the stored coefficients before any colour conversion. With RGB the halo ring would have to be recomputed for three components that all depend on Y, Co and Cg (pixel-domain route: no halo problem, as with chroma in 8d).
- **Recommendation (hypothesis, not a measurement beyond the above).** If the DICOM file must match the viewer's pixels exactly, RGB with the exact route is the simplest and the 3x cost is the price; YBR_RCT exact costs 2.1x and now has its convention (truncation, C1) but Y' must then be recomputed in the pixel domain. Neither exact route is close to the iSyntax size. Only YBR_RCT offers a near-lossless sparse route.
- **Not done:** RGB with a per-tile LL correction, RGB tiles at layers 1-5, omission savings for RGB, the JPEG 2000 Part 1 MCT=0 header details beyond what OpenJPEG writes, the effect of the decoder's clamp on the wavelet-domain route (the clipped counts show it matters in a handful of pixels).
